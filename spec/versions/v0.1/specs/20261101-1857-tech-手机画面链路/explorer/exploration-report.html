2. 参考实现：scrcpy

2.1 帧头格式（server/src/main/java/.../device/Streamer.java:107-125）

8 字节 ptsAndFlags（大端 long）
4 字节 packetSize（大端 int）
共 12 字节
标志值含义
PACKET_FLAG_SESSION1L << 63会话首包
PACKET_FLAG_CONFIG1L << 62配置帧（SPS/PPS），非媒体数据
PACKET_FLAG_KEY_FRAME1L << 61关键帧

2.2 编码参数（SurfaceEncoder.java）

配置值说明
输入COLOR_FormatSurface相机会话直接输出到编码器 Surface，不搬 CPU 帧
KEY_I_FRAME_INTERVAL10（秒）关键帧间隔
KEY_REPEAT_PREVIOUS_FRAME_AFTER100000 µs画面静止时补帧，避免接收端卡住
KEY_LATENCY / KEY_PRIORITY1 / 0低延迟优先
KEY_COLOR_RANGECOLOR_RANGE_LIMITED与解码侧一致即可

scrcpy 用 60fps，本项目按 D-003 用 30fps、1280×720。

2.3 解码（app/src/decoder.c、interop.c）

FFmpeg avcodec_find_decoder → avcodec_open2，硬件解码按平台分派（d3d11va Windows / vaapi Linux / videotoolbox macOS），失败时 sc_decoder_fallback_to_software。选 FFmpeg 的根本原因是它要覆盖三平台与五种编码，不是解码质量。

3. 接入约束（关键）

3.1 发现字段是严格集合

android/.../NsdDiscoveryClient.kt:16：

require(fields.keys == setOf("v", "pcid", "spki", "label"))

多一个字段就会让整台设备被判为非法，不是忽略而是直接解析失败。这与 Spec-1 记录的 EXP-006（严格键校验下不得删字段）是同一类约束。

3.2 已有 TLS 通道

手机与接收服务之间已有 WebSocket over TLS，证书按 SPKI 固定（PinnedTrustManager），配对与信任状态就挂在这条连接上。

3.3 本机 TLS 库

只有 Git 自带的 OpenSSL 3.5.7，没有可链接的开发包。C++ 侧自建 TLS 服务端需要额外引入 OpenSSL 或改用 SChannel，成本不低。

4. 媒体通道的三种候选

方案做法优点代价
A 复用现有 WebSocket媒体帧用二进制 WS 帧发到接收服务，再由接收服务转给本机解码进程零新增 TLS、零发现字段变更、自动继承已建立信任多一跳进程（Node 转发），拷贝开销；控制消息与媒体共用一条连接
B 独立 TCP + TLS解码进程自己监听端口，用同一证书做 TLS 服务端控制与媒体彻底隔离，符合 D-002 原意C++ 要引入 TLS 栈；端口怎么告知手机仍需解决
C 独立 TCP 明文解码进程监听明文端口实现最简单局域网明文可被同网段嗅探；与现有「配对后才可信」的模型冲突

端口如何告知手机

做法兼容性
在 NSD txt 增加 media 字段破坏旧版 App 的严格校验，必须同时升级两端并把 v 提到 3
约定 tlsPort + 1不改协议，但端口被占用时无退路
走方案 A（复用 WS）不需要告知，通道已建立

5. 建议

倾向 方案 A：

  • 避开 C++ TLS 与发现协议变更这两个高风险点，也没有明文传输
  • 720p30 H.264 约 2–4 Mbps，经 Node 转发一次的内存拷贝可以接受；先用真实链路测出延迟，再决定是否值得为省这一跳去写 TLS 服务端
  • 如果实测转发成为瓶颈，再升级到方案 B，那时只需要换传输层，解码与共享内存写入不用动

这与 D-002「独立 TCP」的字面不同，需要在 gate-2 明确改写该决策，而不是悄悄绕过。
