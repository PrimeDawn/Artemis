设计结论

不新造构建体系：安装器只负责摆放、注册、建入口，每个二进制仍由已有命令产出。为了让「装完就能用」成立，本方案先拆掉两个用户机器上不存在的运行时依赖——用纯 JS 在 Node 内签发自签证书（删除 openssl 调用），随包自带 node.exe；再用一个 Artemis.exe 充当进程管家，最后用 Inno Setup 打成逐用户安装包。

1. 概述

1.1 背景

v0.1 的七个 Spec 把链路跑通了，但交付形态仍是「开发机上装好了 Node、Git、VS Build Tools，双击 Start-Artemis.cmd」。探索报告 §3 逐项对照过「只有 Windows 11 + OBS 的机器」：node 不在、openssl.exe 不在（本机那份来自 Git for Windows，且是 MSYS 构建不可搬运）。按这个状态发版，用户装完得到的是「能装不能跑」。

1.2 目标

  1. 产出一个逐用户、免提权的 Windows 安装包，安装后 OBS 能枚举 Artemis Camera 并录出手机画面，全过程不需要 Node、Git、VS Build Tools。
  2. 产出一个可用 apksigner 校验的 release APK。
  3. README 与用户文档重写为使用者口径，并把「音频走 VB-CABLE」这条 D-012 结论讲清楚。
  4. 提供发布线导出脚本，使 spec/、.agents/、.codex/ 等开发资产不进入发布产物。

1.3 范围

包含

  • 证书签发去外部依赖（纯 JS）与 ARTEMIS_OPENSSL_PATH 退场
  • 新增托盘进程管家 Artemis.exe（进程管家 + 控制页入口，不含设置界面、不含开机自启）
  • Inno Setup 安装脚本、安装/卸载的注册与反注册
  • 一键构建脚本 scripts/build-release.ps1 与产物目录 dist/
  • 发布线导出脚本 scripts/export-release.ps1
  • APK release 签名配置与版本号
  • README 重写、两份用户文档、开发文档标注

不包含

  • 代码签名证书、SmartScreen 白名单（用户明确零预算）
  • 自动更新、开机自启、设置面板
  • 自研虚拟声卡驱动（D-012）、VoiceMeeter 支持（D-013）
  • 实际切换 main 分支、创建 GitHub Release（属 version-release，本 Spec 只交付可复用的脚本与产物）
  • FFmpeg 裁剪（143 MB 按用户确认接受）

2.2 非功能需求

  • 可移植：安装包内所有路径相对安装目录解析，不出现开发机绝对路径（EXP-008 的延续）。
  • 可诊断：启动失败必须落到 %LOCALAPPDATA%\Artemis\logs\tray.log，且托盘气泡给出「日志在哪」。

  • 兼容：Windows 10 1809 及以上 x64；不需要管理员权限。

3. 设计方案

3.1 安装后的目录布局

按 D-009，托盘可执行文件与安装器入口统一命名 Artemis.exe（原稿写作 ArtemisTray.exe，全文已同步改名）。

{app}\                                  ; %LOCALAPPDATA%\Programs\Artemis
├── Artemis.exe                     ; 进程管家
├── config.json                         ; 可选覆盖：端口、数据目录
├── runtime\node.exe                    ; 随包 Node 运行时
├── app\
│   ├── receiver\{dist\, node_modules\, package.json}
│   └── native\{artemis-decode-host.exe, ArtemisCamera.dll,
│               avcodec-63.dll, avformat-63.dll, avutil-61.dll,
│               swscale-10.dll, swresample-7.dll}
└── licenses\{FFmpeg-GPL.txt, Artemis-THIRD-PARTY.txt}

用户数据仍在 %LOCALAPPDATA%\Artemis\data（身份、信任、运行锁），与程序目录分离，卸载不删。

3.2 证书签发（FR-001）

3.2.1 数据结构

// receiver/src/cert.ts
export interface SelfSignedCertRequest {
  readonly privateKeyPem: string;  // PKCS#8 PEM 文本，P-256；不可为 EC 以外曲线
  readonly ipAddress: string;      // 点分十进制 IPv4，写入 SAN
  readonly notBeforeMs: number;    // 证书起始时间（UTC ms）
  readonly validDays: number;      // 正数；本 Spec 固定传 30
}
export interface SelfSignedCertResult {
  readonly certificatePem: Buffer; // 证书数组，行为与当前 certificate.pem 一致
  readonly expiresAtMs: number;    // notBeforeMs + validDays*86400000
}

3.2.2 接口

export async function issueSelfSignedCertificate(
  request: SelfSignedCertRequest
): Promise<SelfSignedCertResult>;
// 失败抛 Error（消息含 'cert'），由 identity.ts 统一包成 PairingError('E_IDENTITY', 500)

实现要点：@peculiar/x509 3.1.0 的 X509CertificateGenerator.createSelfSigned，密钥来自 node:crypto 已生成的 P-256 私钥（导入 crypto.webcrypto.subtle，签名算法 ECDSA/SHA-256）。扩展固定为：basicConstraints critical 且 CA=false、keyUsage digitalSignature critical、extendedKeyUsage serverAuth、subjectAltName 含一个 ip 项。主体 CN=Artemis local receiver，序列号为 16 字节随机数。

receiver/src/identity.ts:31loadOrCreateIdentity()删除 await access(config.opensslPath)。其余身份/信任流程不动。

关键决策

证书签发改纯 JS 而非随包 OpenSSL（D-007）：用户机器上本不该有 openssl，「带一份以免调用失败」是把一个本可消除的外部进程固化进交付物。选 @peculiar/x509 而不是手写 ASN.1：证书是安全边界，手写 DER 的错误往往只在特定客户端暴露，而库可以被 X509Certificate.verify() 与 checkIP() 直接验证。被否决项：随包 OpenSSL（+6 MB 且要维护一份 Apache-2.0 声明）、要求用户装 Git（把门槛推回用户）。

关键决策

托盘只做进程管家（D-008），不做设置面板与开机自启。理由是设置面板会把端口、数据目录、网卡选择都变成 UI 问题，而 config.json 已能覆盖这些值；开机自启属产品决策，不该由打包 Spec 顺手决定。

4. 执行模式

推荐模式单 Agent（single-agent）

选择理由改动集中在一条构建链上（证书 → 托盘 → 安装器 → 导出），任务之间是串行依赖，拆多 Agent 只增加交界处返工。

重要

该字段只描述实现阶段由 spec-executor 执行代码修改的模式，不表示整个 Spec 工作流没有项目级角色协作。项目级角色由 spec-init 初始化，spec-start 负责加载和唤起。

6. 验收关注点

  • 证书：新签证书必须能被 X509Certificate.verify() 用同一私钥验证、checkIP(当前IP) 为真、换 IP 为假、有效期 30 天 ±1 天；重签后公钥不变（信任不失效）。
  • 安装：不装 Node/Git 的账户下安装成功；装完 HKCU\Software\Classes\CLSID\{7E1F3A10-…} 存在且 FriendlyName='Artemis Camera'；OBS 能枚举并录出画面。
  • 卸载：卸载后上述 CLSID 键消失、程序目录删除、%LOCALAPPDATA%\Artemis\data 保留。
  • 失败路径：端口占用、无网卡、缺少运行时文件时，托盘给出可读提示且日志落在 %LOCALAPPDATA%\Artemis\logs\tray.log。
  • 导出：导出树中不存在任一开发资产；-Verify 对人为放入的 spec/ 目录返回非 0。
  • 音频边界：未装 VB-CABLE 时，托盘/控制页有明确提示且视频链路不受影响（D-013）。

7. 风险和依赖

风险影响概率缓解措施
@peculiar/x509 在 Node 24 + ESM 下导入或 crypto.webcrypto 集成异常中中任务 1 先写测试；若库不可用，退回用 node:crypto 手写最小 DER（约 120 行）并在报告中记录取舍
托盘 exe 在用户机器上缺 VC++ 运行库高中安装器检测并在缺失时引导安装，或改用静态链接 CRT（/MT）
卸载时子进程未退出导致文件删除失败中中CloseApplications=yes + 托盘退出时先 StopServices；测试用例专门覆盖「服务运行中卸载」
release 签名与 debug 签名冲突，已装手机无法覆盖安装低高README 写明「换签名版本需先卸载重装，会丢失信任，需重新配对一次」
发布线导出遗漏或多带文件中中-Verify 双向断言：黑名单不存在 + 白名单关键路径存在
安装包体积超预期（>150 MB）低中构建脚本打印分项体积；用户已确认 150–200 MB 可接受
风险

托盘 exe 是本 Spec 唯一新增的原生二进制，它与解码进程、Node 运行时是三进程模型。任何一方启动失败都会表现为「托盘在、控制页打不开」，排障必须依赖 tray.log。若实现期发现三进程模型过于脆弱，可降级为「托盘内嵌进程管理但用 --console 模式兜底」，但不能退回只给一个黑框。

注意
