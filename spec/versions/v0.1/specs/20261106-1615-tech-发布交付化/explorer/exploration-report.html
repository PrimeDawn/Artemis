探索结论

打包可做，但「用户机器上什么都没装」这个前提被现有实现违反了三处：启动链路依赖 PATH 里的 node、依赖 openssl.exe 生成证书、依赖 Git for Windows 自带的那份 openssl。安装包不是一个压缩壳，它必须自带这三个运行时并把启动脚本改成显式路径；否则装完照样起不来。 另一个必须先解决的口径问题：README 现在承诺「系统麦克风 `Artemis Microphone`」，而 D-012 已决定不自研驱动、音频只输出到用户自备的 VB-CABLE，文档比产品多承诺了一个设备。

1. 历史经验

记忆库中没有打包类经验（8 条里没有一条讲安装器）。最接近的是 EXP-008 启动脚本不得绑定开发机路径，它记录的正是本 Spec 的起点问题：启动脚本曾把数据目录与 openssl 路径写死在本机，「换一台机器就起不来」的所谓从零复现只验证了开发者机器。EXP-008 已把机器相关输入参数化，但参数化只解决「可以传对路径」，没解决「用户机器上根本没有这份路径」——这一步是本 Spec 要补的。

关键发现

过滤器注册走 HKCU，接收服务也不绑定特权端口（3000/3443/3450 均 >1024）。这意味着整个安装可以不提权，装到 %LOCALAPPDATA%\Programs\Artemis，与 Inno Setup 的 PrivilegesRequired=lowest 天然匹配。代价是：如果 OBS 以管理员身份运行，它会读 HKLM/管理员账户的 HKCU，枚举不到设备——这一点必须写进 README 排障。

4. openssl 的三种收法（影响安装包体积与改动面）

方案做法体积改动面风险
A 随包 OpenSSL安装目录放 runtime\openssl\openssl.exe + libcrypto-3-x64.dll/libssl-3-x64.dll，启动时把 ARTEMIS_OPENSSL_PATH 指过去约 6 MB不改代码，只改启动脚本与打包清单要随包附 Apache-2.0 许可证文本并进依赖清单
B 纯 JS 证书生成用 selfsigned 之类纯 JS 库替换 execFile(openssl, …)<100 KB改 identity.ts 签发路径，需补单测与续签验证触及安全敏感代码；现有「同钥续签 / SAN 校验」用例要改口径

注意

不要直接拷贝本机 C:\Program Files\Git\usr\bin\openssl.exe：它是 MSYS 构建，依赖 msys-crypto-3.dll 等一整套 MSYS 运行库，搬到用户机器会因找不到 DLL 而无法启动。必须用独立的 Win64 静态或自带 DLL 的 OpenSSL 3 构建。

5. 启动形态：原型注释里藏着一个未决项

tools/start-artemis.ps1:2 自己写着「供本机试用，不是最终产品形态（最终形态是托盘常驻程序，留给打包阶段）」。也就是说托盘这件事被上一轮显式推迟到了本 Spec，但它从未被登记成需求。三个可选形态：

形态用户看到什么工作量
控制台窗口一个黑框，关掉就停服最小，等于把现有脚本装进去
PowerShell + WinForms 托盘托盘图标，右键打开控制页/停止/退出，无黑框约一个脚本，无新依赖
独立 Win32 托盘 exe原生托盘，可设开机启动新增一个 native 组件，要单测与构建链改造

这一项必须由用户拍板，它既影响安装包内容，也影响验收标准（「装完能不能用」的判定从「窗口不报错」变成「托盘在、控制页能打开」）。

8. 风险清单

风险

R1 装完起不来：只要漏掉 node.exe 或 openssl 中任何一个，装完就是「能装不能跑」。验证必须在一台没有 Node、没有 Git 的环境里做，只在本机装一遍不算数（本机两者都有，会掩盖问题）。

风险

R2 卸载卸不干净：卸载时若 node/解码进程还在跑，DLL 被占用会导致文件删除失败；而过滤器不反注册，OBS 会留一个打不开的设备项。卸载必须先停进程、再 regsvr32 /u、最后删文件。

风险

R3 APK 覆盖安装被拒：现在是 debug 签名，改 release 签名后已装 debug 包的手机无法直接覆盖，必须卸载重装——卸载会清掉手机里的信任。这不是 bug，但要让用户知道「换签名版本要重新配对一次」。

风险

R4 OBS 与被装用户不同会话：注册在 HKCU，若 OBS 以管理员或其他账户运行，枚举不到 Artemis Camera。属于必须写进排障文档的高频误解。

风险

R5 端口冲突：3000/3443/3450 被占用时启动失败，且现有脚本只把原因打在一个会被关闭的窗口里。安装版至少要给可读提示或日志路径。

风险

R6 GPL 分发义务：随包分发 FFmpeg（GPL shared）必须提供许可证文本与源码获取方式。144 MB 的 DLL 一旦进了安装包，这项义务就从「文档里写一句」变成「法律上必须做到」。

风险

R7 发布线与 dev 漂移：导出是单向的，若有人往发布线直接提交，下次导出会被覆盖。必须把「发布线只写不读」写进文档。

注意

spec-tester 需要覆盖的边界：①无 node/无 openssl 的干净环境安装；②非管理员账户安装与使用；③卸载后 HKCU 下 CLSID 键确实消失；④重装后 OBS 仍能枚举；⑤未装 VB-CABLE 时音频提示明确且视频不受影响（D-013 口径，不验真实出声）。

9. 给下游的建议

  • 输出物：scripts/build-release.ps1（一键构建）、Inno Setup 脚本、scripts/export-release.ps1（发布线导出）、重写后的 README.md 与用户向 docs/、APK 签名配置。
  • 先定两个未决项再动手：openssl 收法（建议 A 随包，零代码风险）、启动形态（建议 PowerShell+WinForms 托盘，成本最低且用户看到的是产品而不是黑框）。
  • 验收顺序：卸载现有开发版 → 用安装包装 → 只按 README 走通配对与 OBS 采集 → 卸载 → 确认注册表与目录无残留。
  • 可复用的现有组件：native/build.ps1（已参数化 VS 与 FFmpeg 路径）、native/register.ps1（已实现注册+校验+反注册+校验，可直接被安装器调用）、tools/start-artemis.ps1（已参数化全部机器相关输入）。
关键决策

不新造构建体系：安装器只做「摆放 + 注册 + 建入口」，所有二进制仍由现有 native/build.ps1 与 npm run build 产出。这样安装包里的每个文件都能追溯到一条已存在的构建命令，验收时出问题可以分别定位是构建错还是打包错。
