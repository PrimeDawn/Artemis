3. 发现并修复的缺陷

缺陷 1：卸载残留正在运行的可执行文件（I-011）

现象：服务运行中卸载，unins000.exe 返回 0、CLSID 已删除，但安装目录残留 7 个文件——Artemis.exe、app\native\artemis-decode-host.exe、runtime\node.exe 与 4 个 FFmpeg DLL，正是当时被占用的可执行映像。

根因：Inno Setup 的 [UninstallRun] 在文件删除之后才执行，taskkill 来得太晚。

修复：改为 [Code] CurUninstallStepChanged(usUninstall) 阶段先 taskkill、等待 1.5 秒释放句柄，再 regsvr32 /u 反注册。复测：残留文件 0、CLSID 消失、数据目录保留。

缺陷 2：端口被占用时没有任何可读提示（I-012）

现象：先占住 3000 端口再启动，--console 打印「services started」，两秒后子进程静默退出，日志只有一句「a service exited unexpectedly」，既没有端口号也没有原因。

根因：托盘不感知子进程失败原因；且 fwprintf 写重定向流时按本地代码页转换，中文变成问号。

修复：启动前用 Winsock 独占绑定探测 3000/3443/3450，命中占用就把「控制页端口 3000 已被其它程序占用…」写进 tray.log 与 stderr；stderr 改为 UTF-8 输出。复测通过。

缺陷 3：控制页重复写响应头，直接把接收服务打挂（I-013）

现象：receiver.log 出现 Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client，随后整个 Node 进程退出；用户看到的是「托盘图标在、控制页偶发打不开、服务自己重启」。

根因：control-http.ts 的 json() 无条件 setHeader；当响应已经发出、后续代码（例如日志回调）再抛错时，catch 里又调用一次 json()，异常从 catch 逃逸成未捕获异常。

修复：json() 与 catch 分支都先判断 res.headersSent，已发送则只 end()。新增回归用例：构造「响应已发出后日志回调抛错」的场景，断言不抛异常且状态码仍为 204；npm test 67 项全绿。

4. 本机环境差异（不计入产品缺陷）

注意：dist\ 目录无法直接运行安装包

本会话在工作区创建的目录会带上一条 Everyone:(CI)(DENY)(DC) 的继承 ACE，Inno 加载器在该目录下解包失败（退出码 1，报 is-XXXX.tmp 无法创建）。同一个 exe 复制到 %TEMP% 后安装正常；测试前已用 SHA256 核对副本与原产物一致。这是本机沙箱写出的 ACL，用户从 Release 页面下载的文件不带该 ACL。

注意：Smart App Control 间歇拦截未签名可执行文件

测试过程中出现过两次 Start-Process 被 SAC 拒绝（事件 3077/3033，Policy {0283ac0f-…}），同一文件稍后又能正常运行。对照：本机未签名的 AgentSpace.Bridge.exe 一直可运行，说明拦截判据是按文件信誉而非「未签名一律拦截」。对用户的实际影响：全新安装的 Win11（SAC 默认开启）可能拦下新构建的安装包，需要用户自行关闭 SAC；这一点已写入 README「已知限制」。
