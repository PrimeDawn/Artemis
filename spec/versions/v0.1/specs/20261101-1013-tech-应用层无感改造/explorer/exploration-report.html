结论

删掉旧接收通道不会改变手机端任何行为：手机从未处理信令，连接状态由 sessionId 决定而非 epoch。改造可以做到手机端零改动，但 PC 端测试需要按用例逐条处置，不能整文件删除。

1. 任务与边界

v0.1 方向已从「手机 → WebRTC → OBS 浏览器源」改为「手机 = Windows 系统摄像头与麦克风」。本 Spec 只做第一层：让代码形态与方向一致，不新增任何媒体或设备功能。

纳入不纳入
删除接收页、接收票据、/ws/receiver 与信令通道摄像头/麦克风采集
保留配对、信任、发现、审批、断开、忘记DirectShow 过滤器、虚拟音频驱动
文档口径同步为系统设备方向更改配对协议字段或握手

2. 关键发现：手机端为什么不依赖接收通道

这是本次改造成立的前提，三条证据各自独立成立。

证据一：手机从不处理信令

android/app/src/main/java/io/github/primedawn/artemis/pairing/ConnectionController.kt:119 为 is ServerEvent.Signal -> Unit，注释写着「Media consumers will be attached by the next Spec」。信令消息到达手机后被直接丢弃。

证据二：连接状态只看 sessionId

ConnectionController.kt:108-113 在 ServerEvent.Session 分支里只判断 value.sessionId != null 就置 CONNECTED，不读取 kind 字段；DeviceClient.kt:70 把 waiting 与 ready 归一到同一条 ServerEvent.Session。

证据三：epoch 缺失时 sessionId 仍然下发

receiver/src/connection-manager.ts 的 sendState() 为 kind=epoch?'ready':'waiting'，但事件体始终包含 sessionId。移除 epoch 后手机收到 waiting + sessionId，仍判定为已连接。

补充：DeviceClient.kt:86-89 的 send() 要求 epoch != null，所以手机本来就发不出信令。接收通道对当前手机端是纯占位。

6. 建议

  1. 实施顺序：先删 PC 端接收通道并让编译通过，再改控制页，最后同步文档。每步跑一次 npm --prefix receiver test。
  2. 删除测试用例时在提交信息里写清「因功能下线删除，非失败规避」。
  3. 验收核心不是「新增了什么」，而是「手机端零 diff + 配对主路径与状态提示逐项照旧」。
