3. WebRTC来源方案与只读检查

官方WebRTC Android源码构建面向Linux，原生源码工具链与下载体量较大。当前Windows项目优先验证可追溯的第三方Maven分发；源码自建保留为候选不满足要求时的升级路线，不在本轮静默增加WSL构建栈。

候选为 io.github.webrtc-sdk:android:150.7871.01，不是Google官方发布的AAR。发布版本v150.7871.01为非预发布，发布于2026-08-31。

检查实际观察不据此推断
Maven AAR49,147,033字节；SHA256 0a1627b1a48c2bc17d9a40d62fc47bd45166f44a311e95917f147c402de379b0文件可下载不等于SDK可运行
ABIarmeabi-v7a、arm64-v8a、x86、x86_64不等于所有Android10+设备已兼容
64位ELFarm64-v8a和x86_64的PT_LOAD对齐为16384；32位库为4096不等于最终APK ZIP对齐、RELRO或16KB设备实测已通过
Java入口包含PeerConnectionFactory、Camera2Enumerator、JavaAudioDeviceModule；Manifest声明minSdk21不等于媒体采集与Android16生命周期已验证
分发差异GitHub发布AAR与Maven AAR的native库一致；433个class仅版本头65→61不同，其他payload一致不能互换两个容器文件的SHA256，也不能把版本头处理当作运行验证
分发差异已找到依据

发布仓库提供downgrade_class_version.py，并由下载/发布链处理Java21→Java17版本头。只读比较与该处理相符；实现时固定Maven坐标和Maven字节哈希，不直接使用不同哈希的GitHub原始附件。

许可证层次

发布仓库自身为MIT，POM声明WebRTC的BSD-3-Clause，另有约788KB的第三方许可证集合。实施时保留对应版本的完整通知与来源索引，不能只写“全部MIT”。本报告不替代后续依赖许可证清单。

4. 对spec-writer与spec-tester的建议

  • Android先建立Wrapper、版本目录和最小Compose Activity，显式声明WebRTC依赖；不在主界面虚构“相机/麦克风已验证”状态。
  • PC只建立TypeScript编译和loopback健康检查服务，不提前实现信令、二维码、TLS或媒体接收。
  • 分别验收依赖来源与哈希、可重复构建、APK64位ELF/ZIP检查、服务启动/退出；本机没有设备时把JNI/16KB/Android10运行项记录为未实测。
  • 业务行为通过RED/GREEN验证；构建配置与静态界面不写镜像实现的无价值测试。
  • 环境补齐、许可证接受、代理和下载校验写明具体入口，不改全局JDK或系统代理设置。

5. 风险与边界

构建环境未齐

Android SDK尚未配置；尚无APK、Gradle编译或真机日志。gate-2前不安装或实施产品工程。

静态对齐不等于完整16KB支持

最终APK需要zipalign检查；若存在GNU_RELRO，还需核对段末端；运行行为必须在实际16KB环境验证。

预编译供应链

候选分发经过发布方的class版本头处理，完整上游到二进制的可复现构建尚未独立重建。本Spec会保存来源、哈希、处理说明和实际构建/运行边界；不满足验收时停止选用并升级。

新知识反思

exp-reflect判断：官方约束和当前候选已覆盖本报告，版本组合尚未构建验证。先不重复写成长期知识；实施验证后再判断是否沉淀。
