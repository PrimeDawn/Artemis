4. 对实现与测试计划的建议

  • 控制页和接收验证页仅在本机HTTP/WS端口；手机使用独立HTTPS/WSS端口。浏览器不接触LAN自签名证书，避免要求用户修改系统或浏览器信任库。
  • 电脑生成带SAN的自签名叶证书，可信电脑控制页通过配对连接串交付证书SHA256指纹与一次性随机码；安卓仅对该连接核验指纹、证书有效期/自签名及默认主机名，错误即中断。
  • 配对120秒、单次消费；发送端会话1小时；接收页需电脑授权的60秒单次票据。撤销/过期立即关闭双端信令，另一接收端不得静默抢占。
  • 本Spec先支持PC二维码展示、安卓手动导入完整连接串和配对状态；相机扫码接入单列后续手机切片。它是规划允许的替代信任入口，不宣称扫码功能已实现。
  • 本Spec验证授权与offer/answer/ICE消息正确路由；不建立音视频PeerConnection，不将信令通道在线等同媒体连接成功。

5. 风险与边界

手机缺席

桌面TLS、JVM测试和模拟器均不能证明S24扫码、跨设备局域网、厂商网络权限或真实OBS兼容。对应项明确not-run。

首次信任依赖电脑端带外信息

使用者须从自己的电脑控制页导入连接串；若配对信息被第三方替换/看到，有效期内可能被抢先使用。该风险不能由媒体加密消除，代码拒绝未知证书和重放，但不声称解决本机恶意软件或肩窥。

IPv4与证书变更

本轮限定用户选择的RFC1918 IPv4；不做自动发现或IPv6。地址/密钥改变须显式重建身份并重新配对。浏览器ICE可能出现mDNS候选，转发器将候选视为受长度限制的不透明数据，不按字面IP过滤。

3. 新的官方来源观察

S-11/S-16支持用DNS-SD/mDNS发现LAN服务；据此提议PC广播服务、手机NSD解析并发送受限presence，使PC能自动列出手机，无需新增手机HTTP服务器。S-12表明旧Android/SDK扩展需要正确管理MulticastLock，不能假设只加INTERNET就覆盖Android10发现。S-15提供纯Node发布接口，不需系统Bonjour安装；实际Windows组播和手机互通仍待实测。

S-13说明系统省电可延后后台网络，因此“无固定到期”与“任何条件下同一socket永不掉线”必须区分；应用负责保活/持久信任/自动恢复，不承诺绕过系统。S-14支持将手机身份私钥保留在Keystore，并以公开身份而非临时IP/短期叶证书记住设备。以上设计是项目推导，尚未实现或验证。

4. 当前方案建议

固定PC与手机公钥身份、首次本机选择+手机一次允许、双方持久信任；后续后台自动挑战认证，无连接期限。PC控制与手机TLS通道分离、自动证书续签保留同一密钥。用户主动断开与取消信任分开，连接故障自动恢复，旧信令epoch失效。默认不自动启动采集。

发现不是身份认证；首次确认是可信LAN内的TOFU选择，不能仅靠设备名宣称首次主动中间人防护已完成。已记住身份遭广播替换/换钥必须拒绝，不静默覆盖。

5. 验证边界
