1. 问题与证据

失败，不是未执行

FG-02在已解锁前台真实手机上失败，手机连不到测试PC。原脚本等的是“已完成认证的设备presence”，却用Native NSD presence描述整个失败，导致误把建链问题归到发现阶段。JDI现场快照显示发现已得到一个候选，opening=1、retries=0、尚无认证challenge。

原始失败快照：真实运行时字段及非零退出结果。它没有线程栈，不能据此断言当时每个底层网络包的去向。下述确定性实验用实际TLS停滞复现相同的候选/开连接/无重试状态，并进一步捕获阻塞位置。

假设实验与结论
新版前台门控完全阻止发现同一APK真实发现/首次允许/常亮均曾通过，诊断发现候选存在；不是持续全部禁用。
Chrome控制页导致发现失败启用/禁用Chrome对照均可成功；未证实，不据此改代码。
mDNS单播绑定IP就是根因原绑定多次成功；通配绑定也出现一次失败，不能构成因果，不改正式绑定或防火墙。

3. 单一可证伪假设及最小实验

假设：android/app/src/main/java/io/github/primedawn/artemis/pairing/PinnedTrustManager.kt:27同时取消了TLS/HTTP升级读取期限；TCP连接成功后若对端停滞，将一直阻塞在TLS握手，android/app/src/main/java/io/github/primedawn/artemis/pairing/ConnectionController.kt:73收不到失败事件，不会安排重试。

实验用真实LAN TCP代理作故障注入：第一条TCP连接已实际accept，但不返回TLS数据；后续连接按字节透明转发真实生产服务。后端只在诊断进程绑定同端口loopback，手机仍连接真实LAN地址，证书、SPKI、主机名、Host端口与协议数据均保持；没有关闭任何身份校验，没有伪造手机或服务响应。没有修改正式APK。

用例实际输出
第一次停滞10.103秒失败，只有1条TCP，未认证；opening=1、retries=0。
第二次相同停滞10.083秒失败，仍只有1条TCP，未认证；同一TLS阻塞状态。
只断开停滞的TCP1.422秒内新连接实际转发生产服务并完成真实签名认证，pass；证明重试本身能工作，缺的是建链失败信号。

命令/非零退出与断言、时间线、两轮连接计数、第一次JDI线程栈、第二次JDI线程栈、真实端点/夹具边界。

线程从SocketInputStream.socketRead0进入ConscryptEngineSocket.doHandshake/startHandshake，再到OkHttp ConnectPlan.connectTls；业务控制器线程空闲等事件。说明卡在TLS建链，不是NSD仍未给地址，也不是在等待用户首次允许。初版代理用了不同端口，被Host校验正确拒绝；该夹具错误保留在tls-gate目录，根因结论使用端口已一致且EOF控制成功的tls-gate-corrected证据。

4. 因果链与修复方案

修复建链期限，保持活动连接无期限

将PinnedTrustManager.kt中建链readTimeout由0改为5秒，保留证书/SPKI/主机名/Origin等校验。超时走已有onFailure→failed→退避重试；5秒后失败，再约1秒重试到健康连接，目标10秒内恢复。已升级WebSocket不设置固定使用期限；callTimeout仍保持0，心跳策略保持。

已经核对本项目锁定OkHttp5.4.0 AAR的实际字节码：WebSocket升级经Exchange.upgradeToSocket调用RealConnection.useAsSocket，后者将socket.soTimeout清为0。因此有限建链读取不等于5秒切断活动WS。本机实际依赖字节码。仍须用真机“建立后跨过5秒空闲”进行短时行为复验。

同时修正状态反馈：实际已有地址并打开传输时显示连接中/正在恢复，不能继续显示正在发现。只在不干扰另一活动电脑/待确认选择时发布该状态。修正测试错误描述，并在失败时保留真实候选/传输阶段，不能把所有建链失败都叫发现失败。

5. 与既有方案的关系

继承update-001和writer/plan的无固定/空闲到期、自动恢复与主动停止保护要求；只修实现偏差，不修改已确认writer/plan.html。生命周期、信任格式、协议和依赖版本不扩张。短期握手期限与活动使用期限本来就应分开。

首次原失败中TLS对端为什么没继续发包尚未逐包证实；本文证实的是会把一次建链停滞升级为不再重试的代码缺陷。它必须先修，再用原完整手机控制流复验。若仍有其它独立故障，继续记录并定位，不用本结论覆盖未知问题。

6. 修复后的验收

  1. 同一个TLS停滞夹具，原先两次失败的控制流都应在10秒内自动恢复真实认证，保持故障首socket不主动释放。
  2. 原始Chrome单击/手机首次允许完整流程成功，真实原生NSD，无发现桥接。
  3. 建立会话后空闲跨过5秒仍是同一session，不因新建链超时而断线；不跑长稳。
  4. 聚焦JVM/TLS负向和受影响回归通过；主动断开、回前台及取消信任保护不退化。
  5. 根因修复后才继续切App、锁屏、省电与回收测试；每轮总计≤300秒，保持公网/E盘，不提交推送PR。
