3. 执行中发现的缺陷

5 个缺陷在执行期暴露并修复

其中 I-002 媒体端口未透传 是真缺陷：-MediaPort 只传给了解码进程，接收服务的 mediaPort 从未从环境变量解析，导致视频永远连到默认 3450 而 PC 上没有监听——表现为「手机在发帧、PC 收不到画面」。已按 TDD 先加失败用例再修。其余四个分别见 实现总结 §2。

延迟测量方法（待执行）

方法 B 时间码回环：PC 全屏显示机器可读时间码（48 个黑白方块编码当前毫秒），手机摄像头拍屏后走完整链路回到 PC，读回该帧并解码方块，与墙钟相减即为「PC 显示→采集→编码→网络→解码→呈现」一圈的延迟，精度约 10 ms。需要把手机对着显示器、配对时点一次授权，其余可自动化。

方法 C 双端时间戳：用手机编码 PTS 与 PC 收帧墙钟做最小延迟估计，得出「编码输出→PC 收到」一段，不含采集与呈现，只能作下界与交叉对照。

方法 A 同框拍摄：外部相机同帧读手机计时器与 OBS 预览，原方案口径，需第二台拍摄设备。

4. 偏差说明

项偏差影响
权限授予用 adb shell pm grant 而非点系统弹窗不改变功能结论；真实用户路径的弹窗文案未在本轮目视确认

首次录制全黑错误设备标识 + 环境无光改用完整标识并在有光条件下重录，最终结果有效；首次黑帧过程已记录
证据形式只保留文本日志，抽帧 PNG 未入库亮度读数写在日志里，可复核；不占用仓库体积

5. 结论

  • 「新用户按文档装一遍就能用」在视频链路上成立：从零安装、一次人工确认、30 秒录制回看有画面、30 fps。
  • 端到端延迟与音画偏差仍未实测，v0.1 不能宣称达到 300 ms / 150 ms 目标。
  • 音频在未装虚拟声卡时按设计降级并提示，符合 D-012/D-013。
