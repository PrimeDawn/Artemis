结论

音频链路照 scrcpy 抄：独立音频 socket、复用同一套 12 字节包头、Opus 优先 AAC 回退、客户端用 regulator 自适应缓冲。这样视频路径一行不用改，也不需要动帧头语义。 最后一跳不自己做：Windows 没有用户态创建录音端点的 API，而微软签名是免费依赖的死结（D-012）。本版改为探测并输出到用户已装的第三方虚拟声卡；没装就没有音频，由用户自决。

1. 现状基线（已合入 dev 的可复用部分）

本 Spec 的前提是「不退化已交付的视频链路」。下列事实来自当前分支代码。

环节现状对音频的意义证据
手机采集 Camera2 输出到 MediaCodec 输入 Surface，编码 H.264，720p30 音频要新增一条独立采集线程，与相机并行 android/.../camera/CameraCaptureService.kt、android/.../camera/VideoEncoder.kt
链路编排 MediaSessionCoordinator 统一持有采集、编码、连接，断线按 1→5 秒递增重连 音频采集与编码必须挂进同一 start/stop 生命周期，否则暂停/恢复会出现半边活着 android/.../media/MediaSessionCoordinator.kt:42-123
手机传输 第二条 TLS WebSocket wss://host:port/media，先发 JSON 绑定（pcId/deviceId/sessionId），通过后才发二进制帧 音频另开一条同构的 /audio，绑定与保活逻辑完全复用 android/.../media/MediaConnection.kt:54-100
帧头 12 字节：8 字节 ptsAndFlags（大端）+ 4 字节长度；bit63 会话首包、bit62 配置帧、bit61 关键帧 不变。音频走独立 socket 后，同一套解析器可直接用于音频流，视频侧零改动 native/decode-host/FrameHeader.h:40-48、android/.../media/MediaWire.kt:16-40
PC 接收 media-relay 校验绑定后把二进制原样写入 sink（decode-host 的 TCP 连接），每 2 秒回保活文本 音频通道复用同一 relay 实现，只是 sink 指向音频输入 receiver/src/media-relay.ts:1-80
PC 解码 decode-host 监听 127.0.0.1:3450，逐帧解析头、缓存配置帧、FFmpeg 解 H.264 → BGRA → 共享内存 音频在独立线程解码与渲染，不回压视频循环 native/decode-host/main.cpp:44-87
系统设备 DirectShow 过滤器从共享内存取 BGRA，OBS 枚举 Artemis Camera 音频侧没有用户态等价物，必须新增内核音频设备 native/artemis-camera/Filter.cpp
零音频代码

Android 侧检索 AudioRecord|RECORD_AUDIO|Audio 只命中一条「断言权限列表不含 CAMERA/RECORD_AUDIO」的既有测试，没有任何音频实现； protocol/pairing-v2.md 也写明「当前没有音频帧类型」。音频是从零开始的一条链路。

2. 参照实现：scrcpy 的音频链路

本项目视频链路本就参照 scrcpy（12 字节包头、MediaCodec 路径），音频继续沿用同一参照，避免另造一套。

环节scrcpy 的做法本项目采用
连接结构 客户端与服务端之间开三条 socket：video、audio、control；音频独立成流，不与视频交织 新增 wss://host:port/audio，与 /media 平级，复用同一 TLS 固定、绑定消息、保活与重连
包格式 与视频同一套 12 字节包头（8 字节 pts+flags + 4 字节长度），配置包先发、重连后重发 完全复用，FrameHeader.h 与 MediaWire.kt 不改语义；音频流里的每一帧天然都是音频
采集与编码 设备侧 AudioRecord → MediaCodec；--audio-codec 支持 Opus（默认）/ AAC / FLAC / RAW；48 kHz Opus 优先、AAC-LC 回退；48 kHz 单声道；码率可配
客户端解码 FFmpeg 解码后交给 SDL 输出设备播放，--audio-buffer 控制缓冲 FFmpeg 解码（Opus 与 AAC 都是原生解码器），输出交给 sink
时钟与抖动 专门的 audio_regulator：按欠载/过载动态调整缓冲与补偿，避免爆音与漂移 同样实现 regulator：目标缓冲 60 ms，在 40–200 ms 间自适应
为什么这条结论重要

音频走独立 socket 之后，帧头不需要再动：不用借 bit60、不用收窄 PTS 掩码、不需要协议版本协商，视频解码路径一行不改。 前一版把音频塞进视频流的方案，等于自己造一个同类实现都没有的耦合点。

3. 最后一跳：不自研驱动，改为输出到用户自备虚拟声卡

系统录音端点只能由内核音频驱动创建，而 Windows 只加载微软签名的驱动；在开源、零预算的约束下拿不到签名（D-012）。因此本版不追求「系统里多一个麦克风」，改为：

  • 探测用户机器上是否装了成对的虚拟声卡端点（CABLE、VoiceMeeter 等），命中则把音频输出到它的渲染端；
  • 用户在 OBS 等软件里选对应采集端，即可收到手机麦克风的声音；
  • 没有虚拟声卡时：视频照常，音频不可用并明确提示，由用户自行决定是否安装。
做法代表项目本版是否采用
纯用户态虚拟摄像头，不做音频UnityCapture、akvirtualcamera、OBS Virtual Camera视频侧已在用同路线（DirectShow 过滤器）
虚拟摄像头 + 额外音频 pin部分 obs-virtual-cam 分支不采用：只对 DirectShow 消费方有效，会议软件看不到
自带签名内核音频驱动DroidCam、Iriun、Camo、VB-CABLE/VoiceMeeter本版放弃：需要 EV 证书与每版提交，与零预算冲突
复用用户已装的虚拟声卡—（本项目的取舍）采用：零成本、零签名；代价是用户自备且需自行配置
产品口径（D-012）

装完 Artemis 即有视频；要有声音，用户需自备一个免费虚拟声卡（CABLE 或 VoiceMeeter），软件自动识别并输出。除 OBS 类软件外的兼容性不在本项目范围。

5. 对下游的建议

给 spec-writer

  • 音频通道与视频通道共用 MediaConnection/media-relay 的实现，只区分路径与 sink，不复制一套重连逻辑。
  • 帧头解析器不加分支：音频流的每一帧都是音频，解析器保持现有语义。
  • sink 抽象三实现：WavFileSink（可判定证据）、WasapiSink（默认设备）、VirtualMicSink（写 Artemis Microphone Feed）。
  • regulator 的目标值必须可注入，便于用假时钟验证，不靠真实等待。

给 spec-tester

  • 解码保真用真实 Opus/AAC 码流，不用手工构造的假帧。
  • regulator 与重连用例用可控时钟与短样本，不安排长时间播放。
  • 系统设备用例依赖驱动与签名条件；不具备时如实记「未实测」，不记为通过。
