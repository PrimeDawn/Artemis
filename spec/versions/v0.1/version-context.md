# Version 运行账本：v0.1

## 1. 版本目标

验证 Artemis 的核心技术路线：在可信局域网内，让 Galaxy S24 / Android 16 的摄像头与内置麦克风通过 WebRTC 同步传入 Windows 上的 OBS 浏览器源，并形成可复现的实验原型和选型证据。

本版本对应产品规划 M0 技术预研。为验证所需建立的最小安卓端、PC 信令服务和接收页属于研究原型；完整产品基础工程、成熟交互和面向普通用户的分发仍属于后续版本。当前已交付最小工具链工程，已记录手机、Android10和16KB模拟器的安装与JNI结果；音视频链路尚未实现。

来源：[产品规划](../../../产品规划.md) 的第 3、4、7、8 节；[版本规划报告](plan.html)。

## 3. 各 Spec 的规划验收边界

### SPEC-sdk-toolchain
- 记录 Android SDK、JDK、Gradle/AGP、Kotlin、Node.js 与 WebRTC SDK 的实际版本及来源。
- 核验 WebRTC 依赖的许可证、原生 ABI、页面大小要求，以及 minSdk 29 / Android 16 目标环境适配风险。
- 从文档步骤可重复构建最小 APK、启动 PC 实验服务；不绑定未经验证的第三方 AAR。
- 输出选型与最小可构建证据；设备访问缺失时明确标记待真机验证。

### SPEC-offline-pairing
- 在断开公网而保留局域网的环境中验证配对和信令，无公共 STUN/TURN、云端信令或在线 CDN 依赖。
- 证明知道 IP 地址本身不能取得媒体接收权限；验证配对有效期、撤销和未配对请求拒绝。
- 对本地 TLS 证书信任、二维码绑定或明确的替代信任方案做可行性验证并记录取舍。
- 不把 WebRTC 媒体加密当作信令安全已解决；若可用方案与产品约束冲突，交回用户决策。

### SPEC-media-obs
- S24 / Android 16 采集一枚系统公开摄像头和内置麦克风，OBS 同时显示画面与收音电平，录制可回看音视频。
- 以 720p / 30 fps 为实验基线，记录实际协商编码、分辨率与帧率；优先验证 H.264 并记录 VP8 兼容路径。
- 媒体直接在手机与 OBS 接收网页之间传输，Node.js 只提供配对、信令和网页，不转码或逐帧中转。
- 单个活动接收端；用户停止后释放相机、麦克风与连接，能够重新启动。

### SPEC-validation-baseline
- 固定并记录手机系统、Windows、OBS、网络环境和构建版本，附验证命令、日志或录像索引。
- 在断公网保留局域网条件下，从首次配对到音视频接收执行一次完整复测。
- 连续推流至少 10 分钟、重复开始/停止至少 3 次，记录异常、资源释放和温升观察。
- 通过可复现方法测量延迟和音画偏差，对照产品目标 300 ms / 150 ms 报告实际结果。
- 输出原型 APK、PC 开发启动步骤、依赖许可证与研究结论；指标超标或设备缺失不得记为达标。

以上 10 分钟 / 3 次是 v0.1 技术预研证据门槛，不替代一期 30 分钟、10 次启停、后台持续运行及兼容性验收。

## 5. 版本验收与发布边界

1. 4 个入版 Spec 完工，分别保留已确认计划、实现记录与真实验证证据；待解决的问题明确登记。
2. 核心音视频链路、离线运行、停止释放和最小持续运行验证通过。
3. 延迟、同步等数据如未达到产品目标，保留差距、处理方案并取得用户明确处置结论，不能宣称已达标。
4. SDK/信令方案可继续支持后续工程化；若关键可行性验证失败，暂停、记录失败证据并重订路线。
5. 达到本研究里程碑验收后，才由 version-release 进行集成验收和实验版发布；预期首个发布 Tag 为 v0.1.0，本次不打 Tag。
6. 1.0.0 稳定发布、Windows 便携包、完整交互、多设备兼容、锁屏和全部一期稳定性验收不在本版本内。
