1. 版本范围与阶段边界

依据根目录产品规划第 8 节，本版本对应 M0 技术预研。最小安卓端、PC 服务及接收页用于验证路线；完整产品工程化和一期能力仍由后续版本交付。

本版纳入后续版本处理
SDK / 工具链来源、许可证、ABI 与可构建性完整基础工程、成熟交互和正式分发
离线配对、信令信任与局域网直连可行性精细的用户引导、自动恢复和全部网络异常交互
单手机、单接收端的摄像头与内置麦克风链路多品牌覆盖、附加镜头、1080p 能力扩展
10 分钟连续运行、3 次启停、延迟和同步实测一期 30 分钟、10 次启停、后台与锁屏验证

一期产品验收目标不变；本版的研究证据门槛不能替代一期验收。

3. 依赖与关键路径

默认推进顺序

SDK 与工具链 → 离线配对 / 信令信任 → 手机到 OBS 的音视频链路 → 真机实测与复现交付。

手机、Windows 与 OBS 的具体版本和可用性在首个 Spec 中盘点。没有目标设备时可以继续资料与构建验证，但不能通过真机验收。各阶段按证据推进，冻结和发布日期不作未经验证的估算。

4. 各 Spec 规划验收

1. SDK 与工具链可行性

  • 记录可核验的WebRTC SDK来源、版本、许可证、ABI和Android版本兼容结论。
  • 按文档可重复构建最小APK并启动PC实验服务，保留命令、环境和结果。
  • 核验Android原生库页面大小要求，明确未完成的真机验证和阻断。

2. 离线配对与信令信任

  • 断公网保留局域网时可完成配对和信令，不依赖公网信令、STUN、TURN或CDN。
  • 验证配对有效期、撤销和未配对请求拒绝，知道IP本身不能取得媒体接收权限。
  • 保留TLS证书信任、二维码绑定或替代信任方案的实测取舍及操作步骤。

3. 手机到 OBS 的最小音视频链路

  • S24与指定Windows和OBS环境中同时接收摄像头画面及内置麦克风，录制可回看音视频。
  • 以720p/30fps为基线记录实际编码、分辨率和帧率，Node.js不转码或逐帧中转。
  • 单活动接收端下可停止采集并释放相机、麦克风和连接，再次启动有效。

4. 真机验证基线与复现交付

  • 固定并记录设备和软件环境，断公网完成配对至OBS音视频接收的端到端复测。
  • 连续推流至少10分钟并重复启停至少3次，保留结果及异常记录。
  • 实测延迟与音画偏差并对照300ms和150ms产品目标，超标项明确处置，不记为达标。
  • 提供可复现实验APK、PC启动步骤、依赖许可证和研究结论；不替代全部一期验收。
性能目标与研究结果分开记录

产品目标为端到端延迟 ≤300 ms、音画绝对偏差 ≤150 ms。v0.1 必须留下真实测量方法与结果；超标时记录差距、根因和后续方案，并取得用户处置结论，不能标为达标。

5. 外部依赖与风险

风险当前认识处理边界
SDK 来源与兼容性尚未选择和验证 WebRTC 二进制依赖核验来源、许可证、ABI、页面大小及 Android 版本，不照搬旧项目依赖
OBS 协商与音频路由实际 OBS 版本和编码协商未验证固定版本、记录 H.264 / VP8 结果，通过录制回看确认声音和画面
局域网直连隔离、防火墙和本地候选可能影响连接记录拓扑，断公网复测，不静默引入公网中继
配对与本地 TLS 信任尚无确定的离线信任方案验证有效期、撤销、拒绝未配对访问；媒体加密不代表信令安全已解决
设备与性能没有真机和指标证据缺设备或关键可行性失败时停在对应验收，不把文档检查当作产品通过

6. 版本发布与交付标准

  • 4 个 tech Spec 均按 R&K Flow 完工并保留真实验证证据，待解决项明确登记。
  • 核心音视频、离线配对与接收、停止释放及最小持续运行通过；研究结论足以支持后续工程化。
  • 指标差距、未验证范围和关键路线失败必须明确处置；不沿用模板中的“四类任务必须全部存在”。
  • 交付实验 APK、PC 开发启动步骤、依赖来源与许可证、实测报告和复现说明。
  • 满足研究里程碑后，通过 version-release 做集成验收并计划发布 v0.1.0；本次不发布。
