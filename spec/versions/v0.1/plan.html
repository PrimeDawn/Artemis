2026-11-01 方向变更

产品形态从「手机 → WebRTC → OBS 浏览器源」改为「手机 = Windows 11 系统摄像头与麦克风」：手机画面通过 DirectShow 虚拟设备 Artemis Camera 出现在 OBS 及其他应用，手机麦克风通过虚拟音频设备成为系统输入。旧接收页、接收票据与 OBS 浏览器源路线作废；配对、信任、发现、信令与前台生命周期行为全部保留且不得退化。

传输已定为 H.264 over TCP：手机 MediaCodec 编码、TCP 上 12 字节包头 + 数据、Windows 端 FFmpeg 解码。设备层与传输层分离（参照 akvirtualcamera 的共享内存 IPC 结构），过滤器只认共享内存中的解码帧。

Spec2自动发现、一次允许后持久信任、无固定使用期限、授权信令与前台常亮/暂停恢复已实现；S24省电锁屏→正常解锁同服务连续验证通过，已原位归档，PR #3待审阅。真实手机换IP未实测；媒体和OBS尚未实现。五分钟测试硬上限已取消，历史长稳仅为旧证据。详情见现状核对报告，下方旧日期内容保留为历史。

版本里程碑目标 · M0 技术预研

在可信局域网内，验证 S24 / Android 16 的摄像头和内置麦克风通过 WebRTC 同步传入 Windows OBS，交付可复现的实验原型、依赖选型与实测结论。在可信局域网内，把 S24 / Android 16 变成 Windows 11 的系统摄像头与系统麦克风：OBS 能枚举 Artemis Camera 与 Artemis Microphone 并录出音画，交付可复现的实验原型、依赖选型与实测结论。

4. 各 Spec 规划验收

1. SDK 与工具链可行性

  • 记录可核验的WebRTC SDK来源、版本、许可证、ABI和Android版本兼容结论。
  • 按文档可重复构建最小APK并启动PC实验服务，保留命令、环境和结果。
  • 核验Android原生库页面大小要求，明确未完成的真机验证和阻断。

2. 离线配对与信令信任

  • 断公网保留局域网时可完成配对和信令，不依赖公网信令、STUN、TURN或CDN。保留无需公网的配对和信令能力；本轮保持公网连接验证局域网配对与信令，通过配置、代码和应用请求记录检查无公网信令、STUN、TURN或CDN依赖；实际断公网运行记未实测，不作为本轮验收阻断。
  • 验证配对有效期、撤销和未配对请求拒绝，知道IP本身不能取得媒体接收权限。
  • 保留TLS证书信任、二维码绑定或替代信任方案的实测取舍及操作步骤。

3. 应用层无感改造

  • 从「OBS 浏览器源」形态改为新方向下仍成立的形态，用户层面无感：配对、信任、发现、连接与恢复行为不变。
  • 删除旧接收页与接收票据机制，清理 /ws/receiver 升级路径及发票据路由；不新增媒体或设备功能。
  • 验收以「不退化」为准：Node 43 项、JVM 18 项测试仍通过，APK 仍可构建，配对主路径照旧，控制页仍能列设备/选设备/断开/忘记。

4. 设备层

  • 参照 akvirtualcamera 结构实现 64 位 DirectShow 源过滤器，通过共享内存 IPC 取帧，先输出合成画面。
  • 验收：OBS「视频采集设备」中出现 Artemis Camera，预览有画面，录制 30 秒回看有画面；不要求其他应用通过。

5. 手机画面进 OBS

  • 手机 Camera2 + MediaCodec 编码 H.264，经已配对鉴权的 TCP 传到 Windows 客户端，FFmpeg 解码后写入共享内存。
  • 以 720p / 30 fps 为实验基线，记录实际编码、分辨率与帧率；媒体不经 Node.js 转码。
  • 验收：OBS 选中 Artemis Camera 能看到手机实时画面，录制 30 秒回看有画面。

6. 音频设备

  • 目标为系统音频输入设备 Artemis Microphone，需要内核音频驱动；spike 可先用已签名第三方虚拟声卡验证路径。
  • 驱动签名作为独立发布门禁，不与功能验收混在一起；不与视频绑在一起验收。

3. 手机到 OBS 的最小音视频链路

  • S24与指定Windows和OBS环境中同时接收摄像头画面及内置麦克风，录制可回看音视频。
  • 以720p/30fps为基线记录实际编码、分辨率和帧率，Node.js不转码或逐帧中转。
  • 单活动接收端下可停止采集并释放相机、麦克风和连接，再次启动有效。

7. 真机验证基线与复现交付

  • 固定并记录设备和软件环境，断公网完成配对至OBS音视频接收的端到端复测。固定并记录设备和软件环境，保持公网连接完成局域网配对至OBS音视频接收的端到端复测；离线功能保留，实际断公网运行记未实测。验收标准改为 OBS 能枚举 Artemis Camera 与 Artemis Microphone 并录出音画；不逐个测试 Zoom/Teams/Windows 相机，也不宣称它们一定支持。
  • 连续推流至少10分钟并重复启停至少3次，保留结果及异常记录。按 D-018 预算内短时实测（录 30 秒回看）、重复启停并记录资源释放；长稳改用代码/状态机审查与边界验证。
  • 实测延迟与音画偏差并对照300ms和150ms产品目标，超标项明确处置，不记为达标。
  • 提供可复现实验APK、Windows 客户端与驱动安装步骤、依赖许可证和研究结论；不替代全部一期验收。

局域网直连隔离、防火墙和本地候选可能影响连接记录拓扑，断公网复测，不静默引入公网中继记录拓扑，保持公网连接检查局域网链路及公网依赖；不静默引入公网中继，断公网运行不宣称已实测
配对与本地 TLS 信任尚无确定的离线信任方案验证有效期、撤销、拒绝未配对访问；媒体加密不代表信令安全已解决首次一次确认、长期身份信任；短期挑战仅限握手，活动连接无固定到期；媒体加密不代表信令安全已解决
设备与性能没有真机和指标证据缺设备或关键可行性失败时停在对应验收，不把文档检查当作产品通过

6. 版本发布与交付标准

  • 4 个 tech Spec 均按 R&K Flow 完工并保留真实验证证据，待解决项明确登记。新增 5 个 tech Spec（应用层改造、设备层、手机画面、音频、真机验证）均按 R&K Flow 完工并保留真实验证证据；已交付的配对/信令行为不得退化。
  • 核心音视频、离线配对与接收、停止释放及最小持续运行通过；研究结论足以支持后续工程化。核心音视频、局域网配对与接收、停止释放及最小持续运行通过；保留离线能力并检查无公网依赖，实际断公网运行不纳入本轮必测门禁且明确未实测；研究结论足以支持后续工程化。核心验收改为 OBS 能同时枚举 Artemis Camera 与 Artemis Microphone 并录出音画。
  • 指标差距、未验证范围和关键路线失败必须明确处置；不沿用模板中的“四类任务必须全部存在”。
  • 交付实验 APK、Windows 客户端与驱动安装步骤、依赖来源与许可证、实测报告和复现说明。
  • 满足研究里程碑后，通过 version-release 做集成验收并计划发布 v0.1.0；本次不发布。
