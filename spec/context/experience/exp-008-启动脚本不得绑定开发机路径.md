# 启动脚本不得绑定开发机路径

## 困境

`tools/start-artemis.ps1` 把数据目录写成 `C:\DEV\ArtemisEnv\receiver-data-run1`、OpenSSL 写成 `C:\Program Files\Git\usr\bin\openssl.exe`。在本机能跑，但「新用户照着文档装一遍就能用」这件事根本没法验证——脚本一换机器就失败，所谓"从零复现"只验证了开发者的机器。

## 策略

1. **机器相关输入全部参数化**：数据目录、外部工具路径、网卡地址、端口都做成参数，默认值指向通用位置（`%LOCALAPPDATA%\...`）而不是某台机器的绝对路径。
2. **外部工具要功能探测，不能只看存在**：PATH 里可能有一个能执行但缺少默认配置的构建（本机就有一个这样的 OpenSSL）。探测时真跑一次最小用例（如 `openssl req` 生成一次性自签名），退出码与产物都在才算可用。
3. **PowerShell 脚本存 UTF-8 BOM**：Windows PowerShell 5.1 读无 BOM 的 UTF-8 会按 ANSI 解码，中文注释直接导致解析错误；用 `pwsh`（7+）时看不出这个问题，容易漏。
4. **探测命令不要用 `&` 直调后判 `$LASTEXITCODE`**：脚本设了 `$ErrorActionPreference='Stop'` 时，子进程往 stderr 写进度会被当成错误抛出，探测永远失败。用 `Start-Process ... -RedirectStandardError` 再判退出码。

## 理由

交付物的第一性要求是"别人拿到能用"，而开发机上的可运行性不能证明这一点。把机器绑定拆掉之后，才能用临时数据目录做真正的冷启动验证；这也是后来能发现「媒体端口未透传」这类只在换配置时才暴露的缺陷的前提。
