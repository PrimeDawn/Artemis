# 未签名的新构建会被按文件信誉拦截

## 困境

测试发布包时遇到自相矛盾的现象：同一个会话里，上午构建的 `Artemis.exe`、`artemis-decode-host.exe` 都能正常启动；下午重新构建后，同样代码、同样构建脚本，`Start-Process` 直接被拒：

```
Start-Process : 由于出现以下错误，无法运行此命令: An Application Control policy has blocked this file
```

Code Integrity 日志给出事件 3077/3033，Policy ID `{0283ac0f-fff1-49ae-ada1-8a933130cad6}`；托盘侧则表现为 `CreateProcessW` 失败、错误码 **4551**（`ERROR_SYSTEM_INTEGRITY_POLICY_VIOLATION`）。等几分钟后重试，同一文件又放行了。

对照实验否定了「未签名就一定被拦」：本机同样未签名的 `AgentSpace.Bridge.exe` 一直能跑。

## 策略

1. **别把「未签名」当判据，判据是「有没有信誉」**。Smart App Control（Win11 全新安装默认开启）按微软 ISG 判定：有签名的、或有足够普及度的文件放行；全新构建、零普及度的文件拦截。等一段时间或重试常常就过了——这说明是异步信誉评估，不是永久黑名单。
2. **区分「本机测试受限」和「用户装不上」**。前者等一会儿再试即可；后者是真实发布风险：用户从 Release 页面下载的正是零普及度的新文件。
3. **报错码要认识**：`CreateProcessW` 返回 4551 = 策略违规；事件 3077/3033 + 上述 Policy ID = CI/SAC 拦截。只看到「文件无法运行」很容易误判成路径或权限问题。
4. **文档里如实写**：SAC 开启的机器需要用户手动关闭（且不可逆），根治只有代码签名证书。不要承诺「装不上是用户操作问题」。

## 理由

把「未签名」当唯一原因会得出「所有用户都装不了」的错误结论（与实测矛盾），也会让人误以为买个证书就能解决一切；把「等一会儿就好」当常态则会掩盖真实的分发风险。正确做法是承认它是按文件信誉的异步判定，然后分别处理本机测试与用户分发两条路。
